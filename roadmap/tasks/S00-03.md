## Не входит

Нет массового рефакторинга runtime, выдуманных live интеграций, OCR корпуса из приватных фото или broad mocks всей функции.

## Критерии приёмки

1. Существующий npm test сохраняет поточні регресії test/ и запускает новые tests; контролируемая неверная fixture выявляется проверкой, пустой обязательный test directory не считается успехом.
2. Fixture fetch разрешает только заданные запросы и отклоняет неизвестную сеть; Chrome storage/identity задаются отдельно в каждом тесте.
3. Тест именования проверяет точный output, date, unknown и suffix; Gmail transport тест проверяет status и payload, а не один факт вызова.
4. Очередной тест не наследует storage, fake clock, fetch или pending promises предыдущего.
5. Реальные client images, токены и depot HTML из рабочего аккаунта не включены в fixtures.

## Test-first и команды

Создать реальные characterization assertions существующего именования/ошибок; наблюдаемый RED должен относиться к неверному поведению harness или явно помеченному дефекту, а не к отсутствию Node.

```sh
node --test --import ./test/helpers/noNetwork.js test/helpers/harness.test.js test/gmail/labels.test.js test/depot/labelName.test.js
```

Виконано 2026-10-23: замість `test/unit/` тести розміщено за чинною модульною
структурою `test/` ([TESTING](../../docs/TESTING.md)); наявний
`test/depot/labelName.test.js` доповнено, а не продубльовано.

Это целевая команда карточки: указанные product test files нужно создать при её выполнении. Их нет в исходном ZIP, и они не объявлены пройденными. Сначала подготовить harness по зависимостям. При изменении имени теста обновить карточку и evidence до заявления о GREEN.

После узкой проверки выполнить затронутые регрессии и обязательные lint/build проверки по [toolchain](../../docs/toolchain.md). Для injected code отдельно проверять serialization, для UI — реальный browser harness. Не выполнять real Gmail/Drive/depot/AI calls по одному разрешению редактировать код.

## Последовательность реализации

1. Выделить минимальные helpers fetch/storage/clock без generic service framework.
2. Написать положительные и отрицательные cases на существующие чистые функции.
3. Расширить существующий test script/harness, сохранив старые cases, и доказать отказ неизвестных внешних вызовов.

## Контракт данных и побочных эффектов

Fake заменяет только внешнюю границу, не тестируемую бизнес-функцию. Наличие synthetic test не доказывает совместимость реального Chrome/Google/depot.

Новый SQL/серверный стек не вводится: сохраняются Chrome + существующий Node bot + Firestore. Изменения config/queue/storage требуют явной совместимости и recovery; не создавать несуществующий src/storage по старому шаблону. Правила безопасности: [security](../../docs/security-and-privacy.md), [контракты](../../docs/contracts.md).
