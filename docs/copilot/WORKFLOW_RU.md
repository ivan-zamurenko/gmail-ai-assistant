## 1. Модель, reasoning и инструменты

Выбор модели должен соответствовать задаче и доступности в аккаунте, а не чужому preset. Для небольшой корректировки docs может быть достаточно обычного режима. Для MAIN serialization, target/origin, мутаций в preview, неопределённого исхода внешней записи и Gmail idempotency требуется тщательный анализ нескольких путей.

Не задавать maximum reasoning для каждой задачи автоматически. Увеличивать глубину, когда есть конкретная неоднозначность или повторяющаяся ошибка. Сильная модель не компенсирует неверную карточку, несуществующий тест или отсутствие внешнего стенда.

Инструменты включать по потребности. Для изменения parser нужны source search, editor и локальный test runner; не нужен доступ к почте. Для review достаточно чтения diff и зависимостей. Наличие connector не является причиной подключать production данные.

Начать с одного writer. Несколько агентов оправданы только независимыми контрактами и изолированными worktrees. Расход оценивать по завершённой проверенной карточке, а не числу ответов или скорости печати кода.

## 2. Контекст и источники истины

Постоянный минимум — AGENTS и `.github/copilot-instructions.md`. CURRENT задаёт состояние, карточка — конкретную задачу, `docs/decisions.md` — подтверждённые решения и предложенные defaults. Подробности домена находятся в целевом контракте.

В начале задачи открыть один раз AGENTS/CURRENT/карточку, затем relevant contract и затронутые source/tests/callers. Расширять поиск при обнаруженной зависимости. Экономия контекста не означает пропуск security-critical callers.

Не прикладывать весь ZIP, все карточки (53), `node_modules`, `dist`, историю `.git` и фотографии накладных. Известный путь или символ лучше общей команды «проанализируй всё». Полные логи хранить локально в безопасном месте; в чат давать релевантный фрагмент и exit code.

Не считать README единственной истиной. В исходном проекте README описывает OpenAI/OCR, которых нет в активном scanner. Комментарий «dry run moves nothing» не проверяет создание папок. При конфликте записать источники отдельно и опереться на требование/воспроизводимое поведение.

Path-scoped инструкции подключаются по правилам выбранного harness. Проверить discovery через customization UI/References, а не утверждение модели. Подробная установка: [COPILOT_SETUP_RU.md](../../COPILOT_SETUP_RU.md).

## 3. Одна карточка

Сначала проверить реальный checkout: ветку, `git status --short`, существующие незакоммиченные изменения. Не копировать baseline SHA из архива как текущую базу. Если задача не дана:

```sh
node tools/roadmap.mjs next
node tools/roadmap.mjs show S00-01
node tools/roadmap.mjs context S00-01
```

Selector read-only. Он не запускает команды из Markdown, не делает commits и не подключает API. При активной in_progress задаче он должен сохранить её приоритет; при pending gate объяснить блокировку, а не сделать ложное done.

Для карточки кратко определить наблюдаемое поведение, допустимые пути и критерии проверки. Не переписывать весь roadmap перед каждой маленькой правкой. Если scope явно слишком велик, разделить до реализации на дочерние карточки с сохранением критериев и зависимостей.

Выполнить только одну ответственность. Например, S01-01 исправляет folder creation в Dry Run, но не внедряет AI, не перестраивает popup runner и не меняет политику disputed labels. Найденные соседние дефекты получают ссылки на свои карточки.

После green остановиться на границе поручения. Если владелец дал диапазон, можно продолжить следующую ready-карточку в нём с новым checkpoint. Не спрашивать «продолжать?» после каждого теста; но не расширять поручение молча.

## 4. TDD и регрессии

Рабочий цикл:

```text
Критерий -> исполнимый тест -> реальный RED -> минимальная реализация
-> GREEN -> затронутые регрессии -> review -> разрешённый commit
-> evidence/state/CURRENT
```

RED означает воспроизведённое нарушение требования. Історичний S01-01 probe відтворював два folder POST. Нині dry-run guard уже є; перевіряти актуальні monthFolders/labelBatch регресії, не вигадувати RED. Missing dependency, Chrome не установлен или fixture malformed — не TDD-доказательство.

До реализации добавить достаточные соседние случаи. В Drive: папки есть/нет, unknown, неподходящий input, ошибка в элементе, live-ветка. Убрать POST только из одного happy path недостаточно. Не менять ожидаемые zero mutations на two mutations ради зелёного теста.

Для parsers/naming — deterministic unit tests. Для external effects — fake transport с точным журналом вызовов. Для injection — сериализованная функция в отдельном контексте, затем artifact. Для Chrome identity/lifecycle — browser layer. Для OAuth и API — разрешённый тестовый аккаунт.

После узкого GREEN запустить affected suite и нужные callers. Полный suite — на PR/вехе или при cross-cutting change. Не повторять одни и те же проверки на неизменённом коде без диагностики flaky behavior.

В новом package уже есть `npm test`; сохранить четыре `test/`. Root и bot dependencies устанавливаются отдельно. S00-03 расширяет harness, а не создаёт первый test script. Future test paths в карточках — то, что нужно создать; отсутствие файла не считается успешным выполнением проверки. Documentation tasks проходят подходящий validator, а не фиктивный unit test.

## 5. Диагностика без бесконечных попыток

После двух безрезультатных исправлений прекратить случайные правки. Сохранить точную команду, минимальный failure output, ожидаемое поведение и две отвергнутые гипотезы. Затем выполнить один диагностический эксперимент.

Примеры: проверить, теряется ли helper при function serialization; показать fake transport call trace; сравнить input shape lookup; проверить реальную версию esbuild и OS; воспроизвести parser на одной synthetic строке. Эксперимент должен отличать гипотезы, а не просто снова запускать тот же тест.

Не отключать lint/security check, не менять всю библиотеку и не расширять сеть для исправления fixture error. После установления причины вернуться к минимальному diff.

При неизвестном business rule задать один вопрос, связанный с gate. Не просить владельца объяснять то, что видно из package/source. При отсутствии внешнего стенда записать env_blocked и не объявлять mock реальной интеграцией.

## 6. Новый чат и checkpoint

Смену чата планировать на границе карточки или модуля. До перехода обновить CURRENT/state/evidence. Сохранить конкретный следующий шаг: файл/команду/непроверенный сценарий, а не «продолжить модернизацию».

В поддерживаемом интерфейсе compact можно использовать для уменьшения истории; конкретная команда зависит от установленной сессии. При её отсутствии достаточно нового чата с корректным checkpoint. Ни новый чат, ни compact не пополняют оплаченный лимит и не заменяют запись состояния.

CURRENT должен указывать task, branch/base SHA, scope, изменения, RED/GREEN, regressions, блокер, rejected hypotheses, риск и commit/push status. Не прикладывать к нему реальные письма, секреты и полные логи.

Новый агент сверяет CURRENT с Git и существующими тестами. Не должен повторно выполнять уже завершённую карточку только потому, что не видел предыдущего чата. Последний commit SHA указывать после его создания, не внутри того же коммита.

## 7. Writer и reviewer

Writer отвечает за один scoped diff и проверки. Reviewer получает карточку, исходный baseline, diff и результаты. Его задача — найти нарушение требований, а не придумать новую архитектуру.

Для DPD особое внимание: preview mutations, неправильная вкладка, MAIN leakage, потеря полей reschedule, guessed endpoints, duplicate filing/drafts, неполная pagination, disputed barcode, invalid scan time, утечка customer data, draft/sent confusion.

Reviewer не меняет code/index/state и не делает внешние вызовы. Реальные tool permissions проверяются отдельно: имя роли read-only не ограничивает инструменты автоматически. Замечание содержит приоритет, путь/место, сценарий, последствие и нужный тест.

Два writer разрешены только после разделения файлов/контрактов и рабочих деревьев. State, lockfile, root config и shared adapters редактирует один integrator. Разные чаты в том же каталоге не дают изоляцию.

## 8. Окружение, поиск и данные

Установка dev dependencies — отдельный шаг с lockfile и зафиксированной версией Node. Не копировать Mac node_modules на другую платформу. Не удалять lock из-за ошибочной установки. Команды сборки запускать из правильного root; `dist` может быть безопасно пересобран только если в нём нет ручной работы.

Сначала source inspection и offline tests. Ни testMode, ни dryRun checkbox не являются тестовым аккаунтом. Реальный Google OAuth, Drive folder и depot session требуют G_TEST_ACCOUNTS и соответствующих domain/privacy approvals.

Search exclude используется только против шума. Он не запрещает прямое чтение `.env` или фотографий и не защищает секреты. Весь staged diff нужно просмотреть перед commit независимо от `.gitignore`.

В error report показывать safe code/operation phase. Не отправлять session/UID из URL, response HTML, адреса и накладные. Для диагностического capture сначала создать синтетическую или редактированную fixture.

## 9. Расход, лимиты и оценка продуктивности

Не закреплять в репозитории чужие цены, перечень «бесплатных моделей» и обещания обхода квот. Проверять фактические условия в интерфейсе своего аккаунта. Новая сессия не обнуляет расход; один запрос владельца может включать много внутренних шагов агента.

Оценивать несколько сопоставимых карточек по четырём показателям: принятый scope, пройденные tests, количество неудачных циклов/review findings и видимый расход. Дешёвый неправильный результат не считается экономией.

Если контекст переполнен — checkpoint и новая сессия. Если задача ходит по кругу — диагностика. Если исчерпан allowance — проверить account budget; не повышать его автоматически. Если возникает rate limit — не запускать плотный бесконечный retry.

Стабильные короткие инструкции и targeted context — предложенный рабочий подход, а не доказательство конкретного процента экономии. Не требовать от модели выдуманных token counts, если интерфейс их не показывает.

## 10. Готовые сообщения агенту

### Выполнить выбранную карточку

```text
Выполни только указанную карточку roadmap/tasks/.
Прочитай AGENTS, CURRENT, decisions и её контракт. Проверь checkout.
Не перечитывай весь архив и не начинай соседние функции.
Сначала исполнимый тест/validator, затем нужный RED, минимальный код,
GREEN и затронутые регрессии. Не ослабляй ожидания.
Используй synthetic fixtures; production и customer data не разрешены.
Обнови CURRENT/state/evidence, проверь diff, укажи commit/push status.
Остановись на границе поручения.
```

### Пример первой дефектной карточки после foundations

```text
Выполни S01-01. В исходном processLabels dryRun=true всё ещё вызывает
getOrCreateFolder до проверки !dryRun. Воспроизведи offline regression
probe, затем сделай preview полностью немутирующим. Не меняй правила
barcode, UI и календарь. Проверь папки есть/нет и live branch.
```

### Проверить diff

```text
Проверь только карточку и diff относительно подтверждённого baseline.
Не редактируй файлы, Git index или state. Проверь negative paths,
внешние эффекты, targets, serialized injection, recovery и data leakage.
Для каждой находки дай место, сценарий, последствие и проверку.
Отдельно перечисли непроверенное. Не переоткрывай весь стек.
```

### Передать состояние

```text
Не начинай новую функцию. Сохрани CURRENT и evidence: task/scope,
branch/base SHA, изменения, точные команды и результаты, blocker,
отвергнутые гипотезы, residual risk и один следующий шаг.
Незавершённое не отмечай done. Secrets/customer data не сохраняй.
```

Полные reusable prompts находятся в [prompts](../../prompts/README.md).

## 11. Чего инструкции не делают

Markdown не устанавливает Copilot, не авторизует GitHub/Google, не меняет модель, бюджет и permissions, не запускает roadmap и не гарантирует соблюдение правил. `.github` не применяет Codex TOML. Skill не создаёт отсутствующие tests или внешний стенд.

Комплект не исправил исходный Dry Run и не реализовал Gmail/AI. Он создал точные требования, воспроизведение и последовательность выполнения. Статусы должны оставаться фактическими.

## 12. Источники и сопровождение

Структура справочника адаптирована из предоставленного WORKFLOW_RU. Домен и команды сверены с ZIP, доказательства находятся в [аудите](../audit/BASELINE.md). Форматы инструкций/ролей/конфигурации сверены с официальными источниками в [SOURCES.md](../SOURCES.md).

Менять правила через небольшой reviewed diff после конкретной повторяющейся проблемы. Удалять дубли и устаревшие команды, но не ослаблять security/acceptance под удобство агента. После изменения Markdown выполнить validators и обновить offline HTML.

## 13. Работа с существующим Discord-ботом

Начать с docs/discord-bot.md/queue-contract.md и выбранной S09 карточки. Для bug в render не открывать весь Gmail roadmap; для смены queue field обязательно прочитать оба mirror, producer/consumer и rules. Один writer управляет общим wire-format и locks; reader проверяет остальные вызовы без редактирования.

В repo две среды: browser extension и Node bot. CLI register/start/deploy выполняют внешние действия, а не проверку обнаружения Copilot. `test/` сохранить; no discord.js — проверить bot install, не переписать тест без зависимости. Нельзя импортировать server config в браузер ради удобства.

Подходящий scoped запрос: «Выполни S09-06. Сохрани существующие карточки /find, явно проверь 12-event history, multi-parcel и минимизированный output. Не меняй roles/queue schema, не обращайся к Maps или depot. В конце покажи точные renderer tests, непроверенное и checkpoint».

При переходе между bot и extension в CURRENT записать оба dependency states, затронутую contract version и что реально проверено. Не выводить реальные uid/keys/customer payload. Проверка postbox и Discord — разные каналы; OWNER-D01 не заменяется todo done.
