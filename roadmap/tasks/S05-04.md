## Не входит

Нет выбора языка по образцу другого проекта, автоответов, компенсаций от имени DPD или скрытого изменения labels.

По OWNER-D01 режим уже выбран: ручная проверка каждого AI-ответа, без auto-send. Эта карточка уточняет остальные правила, но не переоткрывает выбор режима. Ручная отправка остаётся в Gmail.

## Критерии приёмки

1. Подтверждены язык, адресат, reply/reply-all, labels и exclusions; каждый пункт имеет явную policy ветку и тест.
2. No-reply/автоматическое уведомление/спорный адресат/несколько cases не порождают разрешённый draft без необходимой проверки.
3. Ответ не обещает дату, компенсацию или выполненное действие без соответствующего подтверждённого факта.
4. Policy output содержит reason и ссылки на использованные facts; отсутствие данных не заполняется AI догадкой.
5. Auto-send отсутствует. Разрешение draft не превращается в permission менять delivery date или снимать labels.

## Test-first и команды

Test matrix формируется из зафиксированных ответов владельца до реализации policy; до G_GMAIL_POLICY ready отсутствует.

```sh
node --test test/unit/reply-policy.test.mjs
```

Это целевая команда карточки: указанные product test files нужно создать при её выполнении. Их нет в исходном ZIP, и они не объявлены пройденными. Сначала подготовить harness по зависимостям. При изменении имени теста обновить карточку и evidence до заявления о GREEN.

После узкой проверки выполнить затронутые регрессии и обязательные lint/build проверки по [toolchain](../../docs/toolchain.md). Для injected code отдельно проверять serialization, для UI — реальный browser harness. Не выполнять real Gmail/Drive/depot/AI calls по одному разрешению редактировать код.

## Последовательность реализации

1. Записать G_GMAIL_POLICY как конкретную таблицу allowed/denied outcomes.
2. Добавить positive/negative fixtures и проверку unsupported promises.
3. Реализовать чистый decision layer, не смешивая его с transport.

## Контракт данных и побочных эффектов

Продуктовые тексты и business commitments определяются владельцем. Новый baseline использует gmail.readonly. Будущее получение mutating scope требует отдельного решения и само по себе не разрешает send или lifecycle labels.

Новый SQL/серверный стек не вводится: сохраняются Chrome + существующий Node bot + Firestore. Изменения config/queue/storage требуют явной совместимости и recovery; не создавать несуществующий src/storage по старому шаблону. Правила безопасности: [security](../../docs/security-and-privacy.md), [контракты](../../docs/contracts.md).
