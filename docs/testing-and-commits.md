# TDD, регрессии и небольшие коммиты

> **Адаптація до робочого проєкту, 2026-10-23.** Поточний стан і пріоритет рішень: [LOCAL_BASELINE](audit/LOCAL_BASELINE.md). Нижче збережено план комплекту v1.2; його вихідний ZIP і старі перевірки не є поточним checkout. Майбутні задачі не запускаються автоматично. Спілкування з власником — українською.


## 1. Проверка соответствует риску

Чистые parsers/naming проверяются детерминированными unit tests. API adapters — contract tests с явным fake transport и точным журналом эффектов. Depot HTML — synthetic/redacted DOM fixtures. Injection — отдельный контекст после serialization и собранный artifact. Chrome APIs и popup lifecycle — browser tests. OAuth и внешние записи — отдельный разрешённый стенд.

Один слой не заменяет другой. Fake fetch доказывает, какие вызовы делает код, но не проверяет scopes Google. Node import не доказывает MAIN execution. ESLint не проверяет бизнес-политику даты.

## 2. RED

Сначала записать наблюдаемый критерий. Пример S01-01: «при отсутствующих YYYY/MM и dryRun=true число создающих/перемещающих/переименовывающих запросов равно нулю». Затем запустить тест на текущем коде. Історичний probe давав дві POST-записи; поточний код уже має folder/batch регресії. Не видавати старий RED за новий результат.

Не считать RED ошибку импорта отсутствующей библиотеки, недоступный Chrome, ненастроенный OAuth или синтаксическую опечатку самого нового теста. Такие ошибки сначала исправляют как test environment/setup; затем получают падение по нужному поведению.

## 3. GREEN

Изменить минимальный код и сохранить смысл теста. Для Drive это может быть разделение планирования папок и их создания; нельзя удовлетворить тест, просто скрыв POST в другом helper, исключив unknown case или отключив проверку. Добавить adjacent cases: папки есть/нет, unknown, ошибка download, testMode и live branch.

Успех ограниченного сценария не равен завершению всей стадии. Перечислить непроверенные свойства: реальные права Drive, race двух вкладок, shutdown popup, performance декодера.

## 4. Регрессии и разделение test suites

После узкого GREEN проверить affected module и callers. Для injected functions нужен serialization test, для build entries — сборка и проверка artifact. Полный suite обязателен на PR/вехе и при cross-cutting изменении, но не после каждого изменения текста.

Не использовать пользовательские письма/накладные как fixtures. Synthetic fixtures должны содержать явные marker values и проверять негативные состояния. Ошибки не подавлять `|| true`, не заменять отсутствие tests успешным пустым запуском. Нулевое число обнаруженных обязательных тестов — ошибка harness.

## 5. Evidence

Для каждой команды сохранять cwd, точный argv, exit code, краткий результат, тип окружения и очищенный лог. RED/GREEN пары должны относиться к одному требованию и указывать, что изменилось между запуском. На documentation-only задаче допустим validator без фиктивного behavioral RED; это явно записывается как тип проверки.

Commit, push и external approval — отдельные поля. Нельзя выдать code inspection за выполнение теста или state `done` за успешный production run. Формат: [evidence template](../.workflow/evidence/TEMPLATE.json), [handoff](handoff.md).

## 6. Review и Git

До staged changes:

```sh
git status --short
git diff --check
```

Добавить только конкретные просмотренные пути. Затем проверить staged diff:

```sh
git diff --cached --stat
git diff --cached --check
```

Прочитать содержимое staged diff, а не только сводку. Включать тесты и минимальную реализацию одной карточки в один основной green commit. RED сохраняется в evidence; сломанную основную ветку создавать не требуется.

Проверить разрешение commit в текущей среде и subject карточки. После commit получить настоящий SHA; не вычислять и не выдумывать его заранее. Push возможен только при подтверждённых remote/branch/правах, merge — отдельное действие.

## 7. Неуспех

После двух безрезультатных исправлений остановить случайные правки и сделать диагностический эксперимент. Уточнить одну гипотезу: input shape, версия dependency, context serialization, ошибочный fixture или реальный regression. Не переписывать всю архитектуру ради одного красного теста.

Если задача не завершена, checkpoint должен позволять повторить ближайшую ошибку одной командой. Скрывать её за общим «нужно продолжить тестирование» нельзя.

## 8. Новый baseline: тесты расширения и бота

У `test/` є модульні регресії, root test script уже существует. Root `npm ci` и `npm --prefix bot ci` нужны раздельно; bot modules импортируют discord.js. Новые `tests/` не должны скрыть/удалить старый suite. S00-03 добавляет fixtures для Firebase/Discord/Chrome без startup side effects.

Две версии contract и Firestore rules требуют совместной регрессии. Rules проверяются Emulator на allow/deny, а не наличием текста. Сбой reply после успешного depot выполнения проверяется отдельно от ошибки операции; live retry не допускается для получения «красивого green».

[TEST_MATRIX](discord/TEST_MATRIX.md) разделяет source, offline, Emulator, browser и authorized integration. Старые baseline logs — история первого ZIP; новые проверки имеют собственные cwd/source hash и не наследуют PASS автоматически.
