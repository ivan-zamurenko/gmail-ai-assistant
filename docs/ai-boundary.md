# AI-подсистема: отделить планы от работающей интеграции

> **Адаптація до робочого проєкту, 2026-10-23.** Поточний стан і пріоритет рішень: [LOCAL_BASELINE](audit/LOCAL_BASELINE.md). Нижче збережено план комплекту v1.2; його вихідний ZIP і старі перевірки не є поточним checkout. Майбутні задачі не запускаються автоматично. Спілкування з власником — українською.


## 1. Исходное состояние

Исторический README первого ZIP упоминал OpenAI GPT-4o Vision. В актуальном предоставленном снимке сохраняются Gemini-поля конфигурации и константы, но это не доказательство действующего model transport или подключённого settings UI. `src/config/config.js` статически импортирует local.js; прежнюю storage-based схему не считать текущей. В `driveScanner.js` используются локальные ZXing helpers; `src/ai/` и рабочего email-generation pipeline не найдено. Новый [baseline](audit/GITHUB_BASELINE.md) имеет приоритет над описанием первого ZIP.

Поэтому нельзя писать «OpenAI подключён», «Gemini отвечает на письма» или «OCR прошёл проверку». Эти варианты требуют решения владельца. Точную модель, API endpoint, стоимость и параметры нужно проверять после выбора provider, а не брать из чужого эталона.

## 2. Роль AI в выбранном режиме

По OWNER-D01 в [решениях](decisions.md) AI должен готовить текстовый draft proposal по уже собранным подтверждённым фактам, а человек — проверять каждый ответ до отправки. Это выбранная цель разработки, не уже работающая функция. Он не получает credentials, не выбирает произвольные инструменты, не изменяет shipment status и не отправляет письмо. Для barcode первичным остаётся существующий deterministic decoder; добавление AI fallback — отдельный scope и consent gate.

Схема ответственности: extractor → lookup/facts → policy → AI proposal → schema/content validator → human/draft operation. Отсутствие AI не должно ломать deterministic scan и безопасный review workflow.

## 3. Контракт запроса

Вход содержит ограниченное нужной задачей содержание письма, язык по согласованной политике, факты с источниками и запрещённые обещания. Ни токены, ни session URL, ни весь inbox, ни фото накладной «на всякий случай» не передаются.

Вложенные инструкции из письма маркируются как данные. Провайдерский prompt/role не строится простым конкатенированием так, чтобы письмо могло стать system instruction. Model output не интерпретируется как код, URL для fetch или tool command.

## 4. Контракт результата

Предлагается объект с `reply_text`, `needs_human`, `reason_codes`, `fact_refs`. Только разрешённые поля; размер ограничен. Каждая fact reference должна указывать на переданный подтверждённый факт. Новая дата доставки, компенсация, возврат или «точно доставлено» без источника отклоняются.

JSON/schema-valid ответ может быть фактически неверным. Поэтому проверка структуры дополняется policy/content tests. Самооценка модели `confidence` не является автоматическим допуском к send. В режиме OWNER-D01 ручная проверка обязательна для каждого ответа: даже `needs_human: false` не отменяет её. Поле может использоваться как дополнительный сигнал эскалации, но не как разрешение пропустить оператора. Empty/refusal/truncated output даёт безопасный needs_review, а не фиктивный готовый ответ.

## 5. Проверки до внешней сети

Synthetic dataset: одна посылка; несколько; нет совпадения; depot unavailable; invalid scan date; противоречивое письмо; prompt injection; выдуманные tool instructions; запрос чужой персональной информации; слишком длинный ответ; malformed JSON; несуществующий fact_ref.

Зафиксировать ожидаемое поведение и ручные критерии качества до оценки. Не подгонять dataset под один удачный ответ модели. Не называть локальный fake полноценной AI-интеграцией.

## 6. Gate внешнего запуска

G_AI_PROVIDER задаёт provider/model, допустимые данные, бюджет и назначение. G_PRIVACY определяет право передачи и ограничения хранения. G_TEST_ACCOUNTS задаёт тестовый набор. Первая разрешённая проверка — shadow proposal без auto-send и без изменения production.

Отчёт содержит фактический provider/model, даты, конфигурацию без secrets, набор синтетических сценариев, результаты/ошибки и пределы обобщения. Успешный shadow не включает автоматически автоотправку.

До закрытия gates в интерфейсе не должно быть обещания доступного AI. Существующий неиспользуемый key field требует отдельного UX-решения в S07-02, а не удаления credentials пользователя без миграции.

## 7. От shadow к черновику, без auto-send

S06-04 измеряет поведение реальной модели на разрешённом наборе и не создаёт drafts. [S06-05](../roadmap/tasks/S06-05.md) отдельно реализует связку proposal → review/edit → approved draft через S05-05. Для локальной реализации использовать fake transport; для реального межсервисного испытания — S08-03 после разрешений.

Генератор текста не должен владеть возможностью отправки. Будущий auto-send — отдельное изменение policy/orchestration после нового решения владельца; не создавать скрытый переключатель обхода review. Такое разделение позволяет развивать режимы поэтапно, но не является гарантией отсутствия последующей доработки.

## 8. Существующий Discord-бот не является AI transport

`bot/src` обслуживает depot commands, rendering, Maps и todo. Это не реализация model calls и не интерфейс одобрения email. Не отправлять prompt/письмо/AI output в Firestore tasks или Discord без новой утверждённой границы данных. OWNER-D01 и S06-05 сохраняют обязательную ручную проверку; успешный bot pilot не закрывает AI quality gate.
