## Критерии приёмки

1. Валидный proposal отображается вместе с адресатом/thread, фактами и предупреждениями. Ни высокая confidence, ни `needs_human: false`, ни отсутствие предупреждений не вызывают draft creation без явного человеческого подтверждения.
2. Оператор может исправить, отклонить или заново сгенерировать ответ. Подтверждение относится к точной версии текста/адресата/контекста; изменение после подтверждения, смена аккаунта или обнаруженное обновление исходного письма аннулируют старое одобрение. Кнопка создания не использует устаревшую версию.
3. Подтверждённый текст передаётся в S05-05 с проверенными account/message/thread/recipient и operation ID. При успешном ответе UI показывает «черновик создан», но не «отправлено». Некорректный fact_ref, неподдержанное обещание или неразрешённый адресат блокируют этот переход.
4. Повтор нажатия, timeout и partial label failure сохраняют правила single writer/reconcile из S05-05; повтор генерации не перезаписывает ручные правки или ранее созданный draft без нового явного действия. Неопределённый исход не маскируется успешным.
5. На всех fixture-путях — success, edit, reject, regeneration, stale context, resume, timeout — журнал effect-вызовов не содержит отправки писем. Кнопки send и скрытого параметра обхода review нет. Ручная отправка в Gmail находится вне этого execution path.

## Test-first и команды

Сначала задать поведенческие tests: одобренная версия против неутверждённой/устаревшей, ручные правки, две попытки create и полный список effect-вызовов. Проверить RED по отсутствующему поведению, не по отсутствующим зависимостям. Затем минимально соединить существующие границы.

```sh
node --test test/unit/reviewed-reply.test.mjs test/contracts/reviewed-reply-effects.test.mjs
```

Это будущая целевая команда: тестовые файлы надо создать при выполнении карточки. Они не входят в текущий комплект и не объявлены пройденными. После узких тестов выполнить регрессии Gmail drafts, AI validation и затронутого UI, lint/build по [toolchain](../../docs/toolchain.md). Фактическую работу интерфейса проверить в соответствующем browser harness; Node-тесты не заменяют её.

## Последовательность реализации

1. Сверить реализованные proposal/draft contracts и зафиксировать поля approval/revision.
2. Создать fixtures для редактирования, отказа, stale context и uncertain outcomes.
3. Реализовать review/edit и явное одобрение; подключить один draft boundary.
4. Проверить отсутствие send и сохранность пользовательских правок.
5. Зафиксировать результаты, пределы локальных tests и готовность к разрешённому пилоту.

## Контракт данных и побочных эффектов

Approval привязан к account/message/thread/recipient, версии текста и проверенному контексту фактов. Хранить минимум нужных данных и соблюдать согласованную retention policy. Сам output модели не является approval.

Обнаруженное изменение исходного контекста инвалидирует approval. Проверка перед create уменьшает окно устаревания, но не доказывает атомарность между Gmail и локальным storage; остаточную гонку описать и дать оператору актуальный контекст перед ручной отправкой.

Создание draft и изменение labels — разные эффекты; отправка не выполняется. Capability отправки не передаётся генератору. Auto-send возможно только как будущий явно согласованный scope, а не скрытая ветка этой реализации.
