## Не входит

Нет переноса job в worker, смены naming policy, отключения теста или проверки на рабочей папке.

## Критерии приёмки

1. На исходном сценарии с отсутствующими YYYY/MM папками dryRun выполняет ноль Drive create/update/delete запросов; проверяется каждый URL/method.
2. Preview показывает planned folder path и filename без выдуманного remote folder ID; отсутствие папок не мешает preview.
3. При существующей папке и naming collision dryRun по-прежнему не делает PATCH/POST и сохраняет необходимую диагностику.
4. Обычное выполнение создаёт нужные папки только после явного apply и не меняет порядок source parsing/validation.
5. DryRun lookup POST в depot не запрещён механически по HTTP method: тест различает разрешённый поиск и Drive mutation.

## Test-first и команды

Сначала повторить приложенный probe: на неизменённом архивном scanner он возвращает exit 1 и два Drive POST. Это реальный известный RED, не повод ослаблять assertion.

```sh
node --experimental-vm-modules checks/baseline/drive-dry-run-probe.mjs && node --test test/unit/drive-dry-run.test.mjs
```

Это целевая команда карточки: указанные product test files нужно создать при её выполнении. Их нет в исходном ZIP, и они не объявлены пройденными. Сначала подготовить harness по зависимостям. При изменении имени теста обновить карточку и evidence до заявления о GREEN.

После узкой проверки выполнить затронутые регрессии и обязательные lint/build проверки по [toolchain](../../docs/toolchain.md). Для injected code отдельно проверять serialization, для UI — реальный browser harness. Не выполнять real Gmail/Drive/depot/AI calls по одному разрешению редактировать код.

## Последовательность реализации

1. Воспроизвести baseline probe и добавить cases существующих/отсутствующих папок.
2. Отделить расчёт folder path от getOrCreateFolder, перенести создание в apply ветку.
3. Проверить normal path и приложенный probe без реального Drive.

## Контракт данных и побочных эффектов

dryRun гарантирует отсутствие побочных изменений Drive. Получение существующих metadata и разрешённый lookup допустимы. Target plan не маскируется под completed operation.

Новый SQL/серверный стек не вводится: сохраняются Chrome + существующий Node bot + Firestore. Изменения config/queue/storage требуют явной совместимости и recovery; не создавать несуществующий src/storage по старому шаблону. Правила безопасности: [security](../../docs/security-and-privacy.md), [контракты](../../docs/contracts.md).
