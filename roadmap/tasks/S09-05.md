## Acceptance — критерии приёмки

1. Duplicate snapshots и два listener attempts приводят к одному successful claim; tests различают transaction winner и локальную очередь.
2. Execute message от неразрешённого контекста не достигает depot, approved offscreen message проходит; проверка источника не ограничивается полем type из payload.
3. После restart pending сверяется по executorUid/expiry; claimed с неизвестным исходом не перезапускается как новая live-команда.
4. Смена Firebase identity/profile или неверная bot binding не приводит к чтению чужих tasks; выдаётся безопасная диагностика без раскрытия credentials.
5. Ошибки ensureOffscreen/createDocument/heartbeat и недоступный worker управляемы, без нескончаемых retries; browser-проверка не объявляется пройденной на основании Node fixtures.

## Test-first и команды

Если исходная защита уже корректна, сохранить characterization и продемонстрировать чувствительность к контролируемой неверной fixture, не ломать приложение ради RED. Команду запускать после создания теста/подготовки зависимости; для S09-12 show только читает карточку. Затем затронутые регрессии, сохранённый `test/`, lint и нужный build по [toolchain](../../docs/toolchain.md). Не прогонять реальный bot startup как тест imports.

## Контракт данных и эффектов

Сохранить существующий listener, не создавать второй polling service. expiresAt относится к pending claim window, не lease восстановления claimed. Изменённые messages должны оставаться совместимыми и не содержать bot secrets.

Общие источники: [queue](../../docs/queue-contract.md), [Discord](../../docs/discord-bot.md), [security](../../docs/security-and-privacy.md). Различать выполнение бизнес-операции, terminal task, delivery reply и учёт процесса разработки.
