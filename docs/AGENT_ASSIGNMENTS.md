# Агенти: відповідальність і передача роботи

Рішення власника від 2026-10-25: розподілити роботу між агентами, прості рішення,
стислий журнал кожного завершеного кроку, консультація щодо специфіки DPD.
Пріоритет — **driver report S09-13 і його залежності**. Цей документ призначає
області, а конкретне доручення визначає задачу й дозволений обсяг реалізації.

## Швидкий старт для будь-якого агента

1. Прочитай [AGENTS](../AGENTS.md), [CURRENT](../.workflow/CURRENT.md), останні
   записи [WORKLOG](../.workflow/WORKLOG.md), [рішення](decisions.md) та свою картку.
   Далі — обов'язковий контекст AGENTS і лише релевантні контракти/код/тести.
2. Звір `git branch --show-current`, `git rev-parse HEAD`, `git status --short`.
   Не читай приватні конфіги. Чужі зміни не включай у свій commit.
3. Знайди конкретне доручення в CURRENT. Якщо немає виконавця, задачі й дозволених
   файлів — запропонуй наступне доручення інтегратору; не призначай себе сам.
4. Для реалізації застосуй [dpd-task-delivery](../.agents/skills/dpd-task-delivery/SKILL.md).
   Якщо клієнт не підтримує skills, прочитай цей файл як інструкцію вручну.
   Не стверджуй, що автоматичне підключення skill перевірено.
5. До зміни поведінки сформулюй очікування й мінімальний тест на конкретний ризик.
   Спершу відтвори збій, потім зміни код. Якщо поведінка вже правильна, використай
   наявне покриття або characterization і перевір чутливість тесту; не вигадуй RED.
   Наявні тести не дублюй і не послаблюй.

## Як не заважати один одному

- У спільному checkout **один writer**, інші агенти — read-only reviewers.
  Кілька відкритих чатів не створюють ізоляцію. Reviewers не змінюють файли,
  Git index, state, не запускають install/build із записом спільних артефактів.
- До редагування integrator записує в CURRENT: task, роль, конкретну сесію,
  режим, base SHA, дозволені файли, поточний крок і наступну дію.
  Для продуктової задачі оновлює єдині `active_task` та `in_progress` у state.
- CURRENT — передача, а не атомарний lock. Якщо інший агент уже пише або
  статус незрозумілий, новий агент лишається read-only до явної передачі.
  Давня дата запису не є дозволом перебрати роботу.
- WORKLOG/CURRENT/state, evidence, рішення, shared docs, manifest, packages/locks,
  START_HERE та Git index оновлює тільки integrator. Writer передає потрібні
  зміни інтегратору; якщо це одна сесія — виконує їх сам.
- Обидва queue contract.js і firestore.rules узгоджуються як один контракт.
  `executor.js`, `lookup.js`, `depotScript.js`, `depotFlow.js`, `gmailFlow.js`,
  bot `index.js`/`render.js` перетинають категорії: область не дає ексклюзивного
  дозволу на весь каталог, потрібен список шляхів конкретного доручення.
- Справді паралельне редагування — лише після узгодження окремих робочих дерев,
  гілок і непересічних задач. Зараз інфраструктуру для цього не додаємо;
  чинне правило гілки `codex` зберігається.

## Прості рішення та корисні логи

Зберігати наявний стек. Один модуль — одна відповідальність; handlers лише
оркеструють, бізнес-правила не дублюються між popup і Discord. Новий framework,
сервіс логів або універсальна абстракція потребують конкретної користі.

Для майбутніх змін достатньо подій на межах операцій та при збоях:
`component`, `operation`, `phase`, `outcome`, стабільний `errorCode`, за потреби
`durationMs`, `attempt`, випадковий технічний `correlationId`.
Це цільова домовленість, а не твердження про вже реалізований logger.

Синтетичний приклад: `component=discord operation=reply phase=send
outcome=failed errorCode=DISCORD_REPLY_FAILED attempt=1`.
Окремо відрізняти виконання depot, запис queue, доставку Discord і optional Maps/POD.
Помилка доставки відповіді не запускає повтор depot-операції.
Не логувати payload, raw error/provider body, URL сесії, фото, токени, адреси,
телефони або tracking IDs. Повторювані progress-події обмежувати за частотою.
Перевіряти наявні safe-error helpers, а не створювати нові для кожного модуля.

## Коли радитися з власником

Не вгадувати семантику сканів, parcel/event, календар і статуси DPD. Питати,
коли відповідь змінює поведінку, дані для передачі, права, витрати чи великий
рефакторинг. Дати короткий приклад і рекомендований варіант. Решту незалежної
роботи продовжувати; вже погоджені рішення повторно не перепитувати.

Для report ще потрібно визначити спосіб виклику (команда чи дія у /find),
вибір посилки/події та остаточний макет. English, Discord first, без scan history,
Recorded delivery point і ручне перенесення у WhatsApp вже погоджені.
Live/deploy/register, email send та зовнішні дані не дозволяються самим ownership.

## Запис кроку й передача

Після аналізу, test-first, реалізації, перевірки або блокера reviewer/writer
надсилає integrator 1–3 речення. Integrator додає рядок у WORKLOG і актуалізує
CURRENT. Не записувати кожну команду в журнал: точні checks — в evidence задачі.

Шаблон доручення (заповнює integrator у CURRENT):

```text
Task / роль / виконавець-сесія:
Режим: implementation або read-only review
Checkout / branch / base SHA:
Дозволені шляхи:
Поточний крок / зроблено:
Перевірки / неперевірене:
Блокер або питання власнику:
Наступна дія / кому передано:
```

При завершенні: scoped diff, фактичні checks, evidence, status, commit/push,
залишковий ризик, наступна конкретна дія. Не ставити done за результатом аналізу.
Після явної передачі нова сесія звіряє Git заново й починає з незавершеного кроку.

Промпт для підключення будь-якого агента:

```text
Прочитай AGENTS.md, docs/AGENT_ASSIGNMENTS.md і .workflow/CURRENT.md.
Твоя роль: <role>. Доручення: <task ID і scope>. Режим: <implementation/review>.
Спочатку звір фактичний Git і поточного writer. Не бери зайняті файли.
Для реалізації прочитай .agents/skills/dpd-task-delivery/SKILL.md.
Спілкуйся українською, дотримуйся мінімального test-first, передавай короткі
підсумки інтегратору. Питання про специфіку DPD не вирішуй припущеннями.
```
