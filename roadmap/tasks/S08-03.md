## Не входит

Нет массовых customer replies, полномасштабной обработки накладных, произвольного bypass gates или скрытого списания средств AI.

## Критерии приёмки

1. Письменный scope перечисляет конкретные разрешённые effects; draft не подразумевает send, lookup не подразумевает reschedule.
2. Test message -> verified facts -> AI proposal -> human review/edit -> approved version -> confirmed draft проходит по S06-05 с верным recipient/thread и без send; ни один ответ не обходит человека.
3. Drive и depot проверяются отдельными разрешёнными кейсами; отсутствие доступа к одной функции не скрывается зелёным результатом другой.
4. Оператор видит partial/uncertain и выполняет заранее описанный reconcile; нет uncontrolled retries или массового запуска.
5. Результаты пилота и оставшиеся ограничения записаны по capabilities; AI optional scope можно исключить только явным решением и reviewed изменением зависимостей, не silent skip.

## Test-first и команды

Пилот имеет заранее согласованные pass/fail критерии и отдельный checklist. Не провоцировать разрушительные ошибки для искусственного RED.

```sh
node tools/roadmap.mjs validate && node tools/check-docs.mjs
```

Команда уже существует в комплекте. Она проверяет документы/tooling, а не заменяет ручную или внешнюю проверку, описанную ниже.

После узкой проверки выполнить затронутые регрессии и обязательные lint/build проверки по [toolchain](../../docs/toolchain.md). Для injected code отдельно проверять serialization, для UI — реальный browser harness. Не выполнять real Gmail/Drive/depot/AI calls по одному разрешению редактировать код.

## Последовательность реализации

1. Подтвердить capability scope, контакты оператора и способ остановки.
2. Пройти разрешённые сценарии с ручным подтверждением каждого эффекта.
3. Сохранить sanitized evidence, failures и решение о дальнейшем допуске.

## Контракт данных и побочных эффектов

Пилот ограничен объёмом и accounts, не является общим production разрешением. Если AI исключён, изменить roadmap явно с сохранением причины, а не отмечать S06-04 done.

Новый SQL/серверный стек не вводится: сохраняются Chrome + существующий Node bot + Firestore. Изменения config/queue/storage требуют явной совместимости и recovery; не создавать несуществующий src/storage по старому шаблону. Правила безопасности: [security](../../docs/security-and-privacy.md), [контракты](../../docs/contracts.md).

## Критерий завершения

Все сценарии выше проверены на указанном уровне; одна лишь проверка Markdown не закрывает product acceptance. Нет ослабленных expectations, пустых успешных suites и skip вместо обязательной проверки. В evidence сохранены точные команды, cwd, exit codes, граница synthetic/live, непроверенное и остаточный риск. Если не хватает решения или среды, записать blocked/env_blocked и конкретный следующий шаг; не ставить done.

## Review, commit и передача

Проверить `git status --short`, узкий diff и `git diff --check`; staging только просмотренных путей. Разрешение commit/push сверить отдельно. Предложенный subject:

```text
test(pilot): [S08-03] record bounded cross-service evidence
```

Evidence: `.workflow/evidence/S08-03.json`. Обновить существующие CURRENT/state, не заменять их шаблоном. Собственный SHA не записывать внутрь создаваемого коммита. В финале указать фактические RED/GREEN или честное N/A, commit/push status и один следующий task ID.

## Адаптация к bot baseline v1.2

Полный пилот теперь включает S09-12. Условные parcel/barcodes не обязательны: их недоступность показывается честно. При включении optional modes обновить release matrix/dependencies отдельным reviewed решением.

`docs/release-runbook.md` — целевой документ этой карточки, в исходном ZIP его нет. Перед любым разрешённым пилотом создать минимальный runbook с scope, остановкой и сверкой неопределённых операций; после пилота заполнить результат. S08-04 затем дополняет его допуском и rollback. Нельзя ждать будущую S08-04 как скрытую зависимость начала пилота.
