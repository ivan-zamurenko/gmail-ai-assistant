## Не входит

Нет store publish, auto-merge, rollback customer operations без разрешения или заявления о полной готовности при открытых критических рисках.

## Критерии приёмки

1. Названы release artifact/hash, разрешённый канал, scope включённых функций и ответственный за решение владельца.
2. Описана остановка новых jobs и сверка выполнявшихся/uncertain items перед downgrade.
3. Storage version compatibility проверена на синтетическом профиле; старая версия не разрушает новый journal молча.
4. Rollback extension version не называется rollback уже отправленной формы, созданного draft или перемещённого файла; внешние исправления отдельны и разрешены.
5. Фактическая публикация/установка записана только при её выполнении. Без отдельного поручения deliverable остаётся release-ready documentation, не published.

## Test-first и команды

Runbook validator и controlled rehearsal используются вместо фиктивного product RED. Проверка downgrade выполняется в synthetic profile, не на рабочем наборе.

```sh
node tools/roadmap.mjs validate && node tools/check-docs.mjs
```

Команда уже существует в комплекте. Она проверяет документы/tooling, а не заменяет ручную или внешнюю проверку, описанную ниже.

После узкой проверки выполнить затронутые регрессии и обязательные lint/build проверки по [toolchain](../../docs/toolchain.md). Для injected code отдельно проверять serialization, для UI — реальный browser harness. Не выполнять real Gmail/Drive/depot/AI calls по одному разрешению редактировать код.

## Последовательность реализации

1. Сверить capability readiness matrix и оставшиеся risks с владельцем.
2. Пройти остановку/restore совместимости на синтетическом профиле.
3. Зафиксировать go/no-go и ручные шаги публикации без автоматического исполнения.

## Контракт данных и побочных эффектов

G_RELEASE разрешает конкретный выпуск, не force push/merge; Git scope подтверждается отдельно G_GIT. Откат не удаляет evidence и не исправляет неопределённый external state автоматически.

Новый SQL/серверный стек не вводится: сохраняются Chrome + существующий Node bot + Firestore. Изменения config/queue/storage требуют явной совместимости и recovery; не создавать несуществующий src/storage по старому шаблону. Правила безопасности: [security](../../docs/security-and-privacy.md), [контракты](../../docs/contracts.md).

## Критерий завершения

Все сценарии выше проверены на указанном уровне; одна лишь проверка Markdown не закрывает product acceptance. Нет ослабленных expectations, пустых успешных suites и skip вместо обязательной проверки. В evidence сохранены точные команды, cwd, exit codes, граница synthetic/live, непроверенное и остаточный риск. Если не хватает решения или среды, записать blocked/env_blocked и конкретный следующий шаг; не ставить done.

## Review, commit и передача

Проверить `git status --short`, узкий diff и `git diff --check`; staging только просмотренных путей. Разрешение commit/push сверить отдельно. Предложенный subject:

```text
docs(release): [S08-04] define approved rollout and rollback
```

Evidence: `.workflow/evidence/S08-04.json`. Обновить существующие CURRENT/state, не заменять их шаблоном. Собственный SHA не записывать внутрь создаваемого коммита. В финале указать фактические RED/GREEN или честное N/A, commit/push status и один следующий task ID.

## Адаптация к bot baseline v1.2

Rollback включает совместимость bot/extension/schema/rules и безопасную судьбу pending/claimed. Остановка бота не означает отмену already claimed операции. Регистрация команд и rules deployment отдельно контролируются.

Отчёты KIT и аудиты исходных ZIP сохраняются как исторические свидетельства. Новые фактические проверки этой карточки записывать в собственный evidence; не переписывать исторический VALIDATION.md результатами приложения.
