# Безопасность, данные клиентов и пределы автономности

> **Адаптація до робочого проєкту, 2026-10-23.** Поточний стан і пріоритет рішень: [LOCAL_BASELINE](audit/LOCAL_BASELINE.md). Нижче збережено план комплекту v1.2; його вихідний ZIP і старі перевірки не є поточним checkout. Майбутні задачі не запускаються автоматично. Спілкування з власником — українською.


## Статус

Это техническая политика предлагаемого процесса разработки. Она не заменяет внутренние правила DPD, разрешение работодателя, правовую оценку обработки данных или настройки доступа Google. Эти решения отсутствуют в переданных материалах и помечены G_PRIVACY/G_RELEASE.

## 1. Чувствительные материалы

Письма, адреса, имена, номера отправлений, подписи, фотографии накладных, raw depot HTML, session/UID, cookies, Authorization и API keys не включаются в агентские evidence, Git, screenshots отчётов или публичные issues. Даже имя файла может содержать consignment number.

В тестах использовать явно синтетические данные. Для редактированной fixture удалять не только видимый адрес, но и hidden fields, query parameters, script literals, EXIF и embedded payloads. Реальное фото не становится безопасным только из-за замены filename.

`manifest.key` и OAuth client ID — идентификаторы конфигурации; их нельзя автоматически объявлять утёкшим приватным секретом и ротировать без понимания extension identity. Реальные Google tokens и provider keys имеют иной статус и не публикуются.

## 2. Минимальные права агента

Обычная карточка требует чтения исходников, локальных тестов и ограниченной записи в workspace. Ей не нужны подключённые почта/Drive, рабочий Chrome profile и доступ к depot. Подключение таких инструментов повышает риск и должно быть отдельным целевым решением.

Sandbox, tool permissions и approvals важнее просьбы в Markdown. Запрет в AGENTS не является технической блокировкой. Предлагаемые Codex examples оставляют external command network выключенной; это не универсальный firewall для браузера, plugins и других каналов. Подробнее [Codex setup](../CODEX_SETUP_RU.md).

## 3. Приложение и внешние эффекты

Чётко разделять локальную правку кода и выполнение этого кода с боевыми данными. Даже чтение depot может вернуть данные клиента. Создание папки, rename, move, label modify, draft creation, logCall, reschedule и send — разные эффекты с разными допусками.

Dry Run должен проверяться инструментально по всему графу вызовов. Исходный Drive Dry Run не выполняет этот инвариант. Test Mode ограничивает количество фото, но не превращает рабочую папку в sandbox.

## 4. Защита целей

Проверять tab/origin до injection, текущую identity и папку перед apply. Не следовать произвольному `form.action` со страницы без проверки. В MAIN не передавать credentials расширения. Inputs письма/Drive/HTML/AI не могут изменить allowlist или отключить dry-run.

Изменение permissions/scopes должно иметь обоснование каждого права и проверку сценария, которому оно нужно. Нельзя ни расширять доступ «про запас», ни молча удалять нужный scope и выдавать сломанную интеграцию за повышение безопасности.

## 5. Storage и диагностика

Не считать `chrome.storage.local` защищённым хранилищем секретов только по названию local. Доступ и жизненный цикл данных нужно анализировать отдельно. Chrome предоставляет scoped storage API и настройки доступности областей; применимость механизма проверяется по используемой версии. [S-CHROME-STORAGE](SOURCES.md)

Не использовать `clear()` для миграции одного settings key. Ошибки callback API не должны теряться. Смену аккаунта и отзыв token нужно учитывать в queued operations. Retention и удаление journal определить явно; бессрочное хранение всех payloads не является default.

Логи: operation ID, phase, safe error code, counters, timing. Не хранить complete request URL, response body и HTML preview. Для local debug необходимы ограниченный срок, доступ и редактирование перед отправкой. Search exclude/gitignore не запрещают прямое чтение и не обнаруживают secrets внутри кода.

## 6. Review checklist

Изменяет ли preview данные? Может ли target оказаться чужим? Есть ли неконтролируемый повтор mutating request? Что произойдёт после timeout, restart и смены аккаунта? Попадают ли данные в console/errors/evidence? Есть ли авторизованный реальный стенд? Отделён ли draft от sent? Не выдаётся ли эвристика или AI за подтверждённый факт?

Найденная проблема описывается сценарно и привязывается к тесту. Отсутствие находок у reviewer не является сертификатом безопасности.

## 7. Discord, Firestore и конфигурация нового baseline

Текущие защиты: guild check, Administrator для depot-команд, task schema 2, UID binding, transaction claim и ограниченные browser rules. Они уже есть; нужно сохранять и тестировать, а не описывать как отсутствующие. Bot Admin SDK использует другую trust boundary; правила Firestore для browser не заменяют серверные checks.

Исходный manifest теперь использует gmail.readonly и полный drive. Переход к draft/labels требует отдельной проверки scope; не повышать права в рамках документации. Рабочая config импортируется из src/config/local.js, а не загружается активным settings UI из прежнего storage wrapper. Secret values могут быть встроены в dist: ключи бота и service account здесь запрещены.

Ошибки проходят safeErrorMessage, но нельзя объявлять все logger paths безопасными без тестов. Минимизация runFind удаляет имя, улицу, подпись, произвольные notes; consignment/Eircode/drop/операционные routes остаются. Ephemeral ответ передаёт их Discord. Maps также получает геоданные при вызове. Правила payload/retention отдельны от технической возможности передать.

Текущие риски для S09: terminal task удаляется до подтверждения Discord reply; claimed restart не имеет доказанного recovery; sender в worker не проверяется; parcel rules только map, не вложенная schema; optional Maps exception может терять основную карточку. Это не сертификат эксплуатации или воспроизведённая атака, а наблюдаемые точки проверки.
